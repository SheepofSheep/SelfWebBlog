## K01. Spring Boot、IoC、DI 与自动配置

- **重要程度 / 领域**：P0 / Spring。
- **代码位置**：[SelfWebBlogApplication.java:7](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/SelfWebBlogApplication.java:7)，`main`、`@MapperScan`；`WebConfig` 构造器。
- **项目实际应用【源码证实】**：入口创建容器；组件扫描发现 Controller/Service/Configuration，Mapper 扫描生成数据访问代理；构造器注入服务及配置依赖。
- **核心原理【通用原理】**：IoC 把对象创建与装配交给容器；DI 是容器把依赖交给对象。Boot 根据 classpath、已有 Bean 和配置条件装配 MVC、数据源等。引入 starter 不是把所有功能无条件打开。
- **面试标准回答**：“项目通过 Spring Boot 启动，业务类由组件扫描纳入容器。我主要用构造器注入，比如授权拦截器被注入 WebConfig，而不是在业务里 new。Mapper 由扫描注册代理，Boot 根据依赖和配置提供 Web、数据源等默认装配。这样业务更容易替换依赖和测试，但我没有自己实现容器或自动配置框架。”
- **可能追问**：① `@SpringBootApplication` 包含什么？② 自定义 Bean 会怎样影响自动配置？
- **深度解析**：① 组合配置、组件扫描和启用自动配置；扫描范围从入口所在包展开。② 常见自动配置有 `@ConditionalOnMissingBean`，用户 Bean 可使默认实现退让；应查条件报告，而非认为名字相同就覆盖。
- **替代方案与权衡**：手动装配更明确但繁琐；字段注入方便但依赖隐藏、单测不便；当前构造器注入适合此项目。
- **常见误区**：starter 等于实现全部底层；所有 Spring Bean 天然线程安全。
- **掌握建议**：画出入口到一个 Controller 的依赖图，能说明循环依赖原因与条件装配。

## K02. Bean 生命周期与启动顺序

- **重要程度 / 领域**：P1 / Spring、工程化。
- **代码位置**：[DataDirConfig.java:25](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/config/DataDirConfig.java:25)；`DatabaseInitConfig.seedDatabase:21`；`ImageAssetService.reconcileStagedDeletions:69`。
- **项目实际应用【源码证实】**：静态 `@Bean` 的 BeanFactoryPostProcessor 提前创建数据目录；Runner 初始化管理员、站点和旧数据；图片服务 `@PostConstruct` 恢复暂存删除。
- **核心原理【通用原理】**：定义注册、实例创建、依赖注入、初始化回调和后处理不是同一阶段；Runner 在容器启动后的应用启动阶段执行。BeanFactoryPostProcessor 主要处理 Bean 定义，此处还执行目录准备。
- **面试标准回答**：“SQLite 文件需要先有父目录，所以项目在数据源创建前准备目录。正常 Bean 完成依赖注入后会执行初始化回调，图片服务借此恢复上次未完成的删除。管理员种子数据则由 Runner 写入。需要把这些阶段区分开，不能因为都是启动代码就默认彼此顺序可靠，也不能在 PostConstruct 中依赖自己的事务代理。”
- **可能追问**：① PostConstruct 调用本类事务方法是否有事务？② 多个 Runner 如何排序？
- **深度解析**：① 初始化对象不等于通过已完成的代理调用；自调用绕过代理，需要外部代理或显式事务。② 可用 Ordered/Order 表达依赖；相同或未指定顺序不宜建立隐式依赖。
- **替代方案与权衡**：部署前创建目录更简单，但开发启动体验不同；Flyway 适合 schema 演进，Runner 适合明确的种子或兼容处理。
- **常见误区**：所有 Bean 都已实例化才执行任意初始化；启动迁移天然只读。
- **掌握建议**：能排列本项目目录、Flyway、种子数据三个阶段；理解启动服务可能写真实数据。

- **代码位置**：[WebConfig.java:64](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/config/WebConfig.java:64)；`AdminAuthorizationInterceptor.preHandle:40`、`findPolicy:76`。

- **核心原理【通用原理】**：Filter 包住 Servlet 请求链，MVC 拦截器在 Handler 已匹配后执行，因此后者能看 HandlerMethod 的注解。DispatcherServlet 负责分发，消息转换器处理 JSON。
- **面试标准回答**：“项目先用 Filter 处理与业务方法无关的身份、CSRF 和追踪，再用 MVC 拦截器读取 AdminOnly 判断管理权限。JwtFilter 设置请求里的用户身份，拦截器以数据库角色判断。前端隐藏按钮只是交互措施，真正授权在后端。这里不是 Spring Security 默认认证链，也不是我写了一个 AOP 切面。”
- **可能追问**：① Filter 抛异常会进入 ControllerAdvice 吗？② 拦截器能保护非 MVC 资源吗？
- **深度解析**：① 通常不能，异常发生在 DispatcherServlet 外；Filter 要自身处理或统一外层机制。② 它依赖 MVC Handler，不应替代覆盖所有入口的安全 Filter；新 Servlet/管理端点需单独检查。
- **替代方案与权衡**：完整 Spring Security 对复杂授权更成熟；小系统自定义链直观，但容易遗漏旧路由。
- **常见误区**：`@AdminOnly` 是 Java 注解所以自动生效；前端路由保护等于安全授权。
- **掌握建议**：按顺序讲完整请求链，找出匿名请求何处变成 401/403。

## K05. JWT 的签发、校验与撤销

- **重要程度 / 领域**：P0 / 安全、认证。
- **代码位置**：[JwtUtil.java:29](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/security/JwtUtil.java:29)，`generateToken/parseToken`；`JwtFilter.doFilter:30`；`AuthController.logout:443`。
- **项目实际应用【源码证实】**：JWT 包含 subject、role、tokenVersion、签发与过期时间；用 HMAC key 签名，算法由库和 key 决定。Filter 从 Cookie 读 Token，验签后查用户与版本，角色取数据库。
- **核心原理【通用原理】**：签名保证完整性和签发者可信，payload 可解码，不提供保密。纯 JWT 可不存会话记录，但本项目加入用户状态校验，用数据库实现撤销。
- **面试标准回答**：“本站 JWT 存在 HttpOnly Cookie，服务端先验证签名和过期时间，再查用户，对比 tokenVersion，并使用当前数据库角色。退出会递增版本，旧 Token 即使没到期也不能再认证，而且会影响该用户其他旧会话。默认有效期七天，没有 refresh 流程。所以我会说这是带数据库撤销检查的 JWT 认证，而不是完全无状态方案。”
- **可能追问**：① 为什么退出不能只删浏览器 Cookie？② 密钥泄露或用户被删会怎样？
- **深度解析**：① 被复制的旧 Token 仍可重放，需要服务端撤销依据。② 密钥泄露可伪造签名，应轮换并拒绝旧凭证；本项目用户不存在则匿名，但密钥轮换机制尚未实现。
- **替代方案与权衡**：Session 更自然地管理单会话；短 JWT+refresh 提高生命周期控制但需刷新、撤销、重放防护。
- **常见误区**：JWT 加密、无需数据库、退出自动撤销、已经实现刷新或固定使用 HS256。
- **掌握建议**：能跟踪一次 Token 生成到失效，说明版本读改写的并发风险与原子更新建议。

## K06. Cookie、Session、CSRF 与 CORS

- **重要程度 / 领域**：P0 / 网络、安全。
- **代码位置**：[SessionCookieService.java:18](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/security/SessionCookieService.java:18)；`CsrfFilter`；`WebConfig.corsConfigurer:49`；前端 `client.js:1`。
- **项目实际应用【源码证实】**：会话 Cookie HttpOnly、SameSite=Lax、Secure 可配置；可读 XSRF Cookie 与请求头比较，unsafe 方法要求通过；CORS 限定来源并允许 credentials。未使用 HttpSession 保存业务登录状态。
- **核心原理【通用原理】**：Cookie 是浏览器传输和存储机制，Session 是服务端会话机制。CSRF 利用浏览器自动携带凭证；跨源读取限制不等于阻止所有跨站写入。
- **面试标准回答**：“JWT 放 Cookie 可以减少脚本直接读取 Token 的机会，但浏览器自动携带 Cookie，所以项目还有双提交 CSRF：先取可读 token，写请求放到 X-XSRF-TOKEN，后端与 Cookie 常量时间比较。HttpOnly 不能阻止 XSS 在本站发请求，SameSite 也不能替代所有防护。CORS 解决允许哪些来源读取响应，不是后端权限系统。”
- **可能追问**：① 跨源和跨站有什么区别？② Session 和 JWT 都能放 Cookie 吗？
- **深度解析**：① origin 由 scheme/host/port 决定，site 通常按 scheme 与可注册域判断；部署跨站时 Lax 可能限制 Cookie。② 可以，存储位置与凭证类型是两个维度；Session ID 查服务端状态，JWT 可验证自带声明。
- **替代方案与权衡**：Authorization Bearer 减少自动携带式 CSRF，却要解决 JS 持有 Token 的 XSS 风险；本项目没有 Bearer 路径。
- **常见误区**：JWT 天生不怕 CSRF；允许 credentials 时随意使用 `*`；Secure 表示整个网站已经 HTTPS。
- **掌握建议**：用浏览器网络面板辨认 Cookie、预检和 CSRF 403；不会把 XSRF token 称为登录 JWT。

## K07. BCrypt、管理员密码与凭证轮换

- **重要程度 / 领域**：P0 / 安全、Java。
- **代码位置**：[UserService.java:30](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/service/UserService.java:30)，`register/login`；`DatabaseInitConfig.ensureAdminUser:34`；`AuthController.login:244`。
- **项目实际应用【源码证实】**：注册对密码 BCrypt 编码，登录 matches；管理员还存在配置密码分支。已有管理员启动时只同步角色，不同步 hash 或版本，导致密码轮换边界问题。
- **核心原理【通用原理】**：密码存储需要带盐、可调成本的单向算法；BCrypt hash 包含算法、成本、盐等信息。随机盐使同一密码不同存储值，不能重新 encode 后字符串相等比较。
- **面试标准回答**：“普通用户用 BCrypt 存密码，登录通过 matches 验证，数据库不保存明文。BCrypt 的成本可以减慢离线猜测，但还需要在线限流。管理员当前同时有配置和数据库两个凭证来源，我审查发现只改环境变量不会废掉数据库旧 hash，旧密码仍可能登录。应明确权威来源，并在密码变化时处理 hash 和 tokenVersion。”
- **可能追问**：① 为什么不用 MD5 或 SHA256？② 改密码后旧登录态是否应失效？
- **深度解析**：① 快速通用散列适合完整性，不适合抵抗密码字典；加盐也不能弥补计算成本过低。② 通常应按策略撤销旧会话；原子更新版本避免并发丢增量，且要考虑管理员首次绑定身份。
- **替代方案与权衡**：Argon2 等是可选密码算法；迁移需要识别存量 hash 并逐步升级，不是直接替换所有存储。
- **常见误区**：密码“加密后可解密”；环境变量更改天然等于数据库凭证变更。
- **掌握建议**：说清盐、成本、matches 和轮换；不要在演示或报告中展示实际凭证。

## K08. OAuth 授权码、state 与一次性 ticket

- **代码位置**：[AuthController.java:298](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/controller/AuthController.java:298)，`githubLogin/githubCallback/exchangeOAuthTicket`；`OAuthStateService:13`；`OAuthLoginTicketService:15`。

- **面试标准回答**：“用户先跳 GitHub，后端验证 state 后拿 code 去换 GitHub access token，再取 GitHub 用户 ID 建立本地身份。后端不把本站 JWT 放 URL，而是发一个两分钟、只能消费一次的 ticket，由前端 POST 兑换 HttpOnly Cookie。state 和 ticket 都在本地 Guava，适合单实例；我没有实现 PKCE、分布式状态或自动账号绑定。”
- **可能追问**：① 有 code 为什么还要 state？② GitHub login 与本地用户名同名怎么办？
- **深度解析**：① code 不能独自证明本浏览器发起请求，state 防登录流程串换。② 稳定外部 ID 才是身份；当前直接用 login 作为唯一 username 会冲突，不能为方便按名字自动绑定他人账号。
- **替代方案与权衡**：成熟 OAuth2 client 框架减少协议代码；统一身份表支持多提供方，需额外绑定和解绑策略。
- **常见误区**：OAuth 就是加密登录；scope 申请等于所有资料已同步；当前缓存抗跨实例重放。
- **掌握建议**：画六个参与步骤，解释 state、code、第三方 token、ticket、本站 JWT 各自用途。

## K09. IP 隐私、HMAC、AES-GCM 与代理信任

- **重要程度 / 领域**：P1 / 安全、密码学。
- **代码位置**：[IpCipher.java:37](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/interaction/security/IpCipher.java:37)；`VisitorIdentityService.hash:22`；`ClientIpResolver:20`；`AdminInteractionController:95`。
- **项目实际应用【源码证实】**：IP 密文用于受权限和审计约束的查看；HMAC 标识用于信任、去重等比较；注册 IP 旧数据迁移去明文。只有连接来源属于可信代理时才读转发头。
- **核心原理【通用原理】**：AES-GCM 同时提供加密和完整性验证，nonce 不能在同 key 下重复；HMAC 引入秘密，避免小范围 IP 被公开散列枚举。Base64 只是编码。
- **面试标准回答**：“项目把 IP 的两种用途拆开：需要管理员追溯时保存 AES-GCM 密文，日常比较使用 HMAC-SHA256 标识，公开 DTO 不返回这些敏感字段。取 IP 时只信任配置代理，不能直接相信客户端 X-Forwarded-For。HMAC 仍是可关联标识，不代表数据完全匿名，密钥和代理配置都要保护。”
- **可能追问**：① SHA256(IP) 为什么不够？② 随机 nonce 和 key 丢失有什么后果？
- **深度解析**：① IPv4 空间可枚举，攻击者可预计算；HMAC 需要 secret。② nonce 重用破坏 GCM 安全；加密 key 丢失不能恢复历史明文，换 HMAC key 则影响历史标识比较，需版本与迁移策略。
- **替代方案与权衡**：不存可逆 IP 更少敏感数据，但无法满足相同追溯能力；脱敏截断适合粗粒度统计。
- **常见误区**：加密字段等于访问控制已完成；所有代理头可信；相同 IP 就是同一人。
- **掌握建议**：区分散列、MAC、加密、编码，并能解释 NAT 和 User-Agent 对去重的影响。

- **重要程度 / 领域**：P0 / 数据库、并发。
- **代码位置**：[application.yml:94](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/resources/application.yml:94)；`InteractionMapper.acquireWriteLock:14`；`EngagementMapper.acquireWriteLock:12`。

- **替代方案与权衡**：MySQL 多写者行锁更适合增长，但带来运维和迁移；当前先量测数据库等待与慢请求。
- **常见误区**：WAL 无锁、池越大越快；把 SQLite 默认隔离口述成 InnoDB RR。
- **掌握建议**：画读快照和写事务示意，解释锁范围；测试并发正确性与压测容量分开。

- **核心原理【通用原理】**：以常见 HTTP/1.1 或 HTTP/2 为例，域名解析获得地址，TCP 建可靠字节流，HTTPS 再有 TLS 验证与加密，HTTP 表达应用请求；HTTP/3 使用 QUIC 而非 TCP。连接和 DNS 可能复用/缓存。
- **面试标准回答**：“开发时浏览器请求相同前端源，由 Vite 把 API 代理到 8080，生产架构仓库不能证明。对常见 HTTPS 连接，可以从 DNS、TCP、TLS、HTTP 四层解释，TLS 保护传输但不解决权限。反向代理终止 TLS 时，后端要正确识别外部 scheme 和可信客户端 IP，否则 Secure、HSTS 和限流可能与预期不符。”
- **可能追问**：① TCP 三次握手和四次挥手为何？② 代理后为什么不能信任任意 forwarded header？
- **深度解析**：① 握手确认双方序号和双向通信能力；关闭两方向可独立，FIN/ACK 可合并，不保证总是四个包。② 客户端能伪造头，代理要覆盖清理，后端只信受控链；当前只做精确可信 IP 配置。
- **替代方案与权衡**：同源代理简化浏览器部署；跨源 API 需 CORS/Cookie 策略。没有必要为博客直接引入服务网格。
- **常见误区**：HTTPS 防 XSS；Cookie Secure 自动配置 TLS；请求每次都新建 TCP；本项目已用 Nginx。
- **掌握建议**：能顺着地址栏一次访问解释缓存、连接、TLS、代理和 API 状态，不编造线上拓扑。

## K29. 日志、健康检查、故障排查与性能优化次序

- **重要程度 / 领域**：P1 / 工程化、系统设计。
- **代码位置**：[RequestTraceFilter.java:24](E:/AAZ-StudyProfileslib/SelfWebBlog/SelfWebBlog/src/main/java/org/example/selfwebblog/security/RequestTraceFilter.java:24)；`SecurityAuditService:15`；`AdminDashboardController:55`；`application.yml:19`。
- **项目实际应用【源码证实】**：请求 ID 放 MDC、响应和 Result，finally 清理；操作审计落数据库；Actuator 只暴露 health。面板数据库状态在查询后填固定 UP，不是持续监控；未见告警、APM、负载基线。
- **核心原理【通用原理】**：日志、指标、追踪分别提供事件、趋势和链路信息；MDC 通常线程上下文，线程池复用时必须清理。优化应先分辨浏览器、网络、线程/连接等待、SQL、磁盘和 JVM。
- **面试标准回答**：“项目已有请求 traceId，前后端错误能用它关联服务端日志，管理行为也有审计。health 只能说明某一时刻检查结果，不能替代告警和性能指标。遇到慢请求，我会先看响应和日志，检查连接池、SQLite 写锁、SQL 返回量、图片解码和磁盘，再优化具体原因。仓库没有线上故障或压测证据，排查经历需本人确认。”
- **可能追问**：① traceId 就是分布式追踪吗？② 测试通过和可观测性如何关联？
- **深度解析**：① 单服务相关 ID 没有跨服务 span、采样和传播系统，不等于分布式 tracing。② 测试验证已知行为，日志和指标帮助解释运行时未预见情况；任何指标都需定义口径和采集成本。
- **替代方案与权衡**：先补关键错误与延迟可见性、恢复演练；完整 APM 取决于维护需求，不能包装为已实现。
- **常见误区**：固定 UP 是可用率；有审计就有全量安全监控；测试数量等于覆盖率。
- **掌握建议**：准备一个明确标为假设的 500/慢请求排查路径，区分真实记录与设计推演。
